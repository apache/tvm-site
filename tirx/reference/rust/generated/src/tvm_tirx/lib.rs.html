20//! The TIRx compiler in Rust: its IR objects over TVM FFI, and the definition of new types,
21//! operators and passes that extend it.
22//!
23//! The IR bindings are generated by `tvm-ffi-stubgen --target rust` from the reflection metadata of
24//! `libtvm_tirx_compiler`. The modules follow the Python package `tvm_tirx`:
25//!
26//! - [`ir`]: the shared IR (expressions, statements, types, functions, modules and operators),
27//!   with the primitive expressions in [`ir::prim`] and the pass infrastructure in
28//!   [`ir::transform`].
29//! - [`tirx`]: tensor functions and types, index maps, layouts, thread scopes, structural
30//!   traversals, tile instructions and the TIRx passes.
31//! - [`sym`]: symbolic analysis: the analyzer, constraints, integer sets and iterator maps.
32//! - [`target`]: compilation targets and target kinds.
33//! - [`backend`]: backend-specific objects, such as the attributes of CUDA instructions.
34//! - [`runtime`]: the runtime objects the IR refers to, tensor allocation and runtime queries.
35//! - [`codegen`]: compilation of IR modules into runtime modules, and the LLVM backend queries.
36//! - [`script`]: printing IR objects as TVMScript.
37//!
38//! # Using the bindings
39//!
40//! The crate links `libtvm_tirx_compiler`, so its type keys and global functions are registered
41//! when a program starts. The build script finds the library through `tvm-tirx-config --libdir`,
42//! as `tvm-ffi-sys` finds libtvm_ffi through `tvm-ffi-config --libdir`: both helpers come with
43//! their Python packages (`apache-tvm-tirx` and `apache-tvm-ffi`) and must be on `PATH` when the
44//! crate is built. The native global functions have Rust wrappers, as methods of the handle types
45//! and as functions of the modules, such as [`target::Target::new`] for `target.Target`. Native
46//! functions that have no Rust wrapper are called through [`tvm_ffi::Function::get_global`].
47//!
48//! The crate uses the library only through the TVM FFI registry, so a linker that drops
49//! unreferenced libraries (`--as-needed`, which rustc passes on Linux) keeps it only because
50//! the crate holds a reference to a symbol of it, the link anchor, that is linked along with the
51//! crate. A program that calls at least one wrapper therefore has the library as a dependency,
52//! at no run-time cost. A program that reaches the registry only through `tvm_ffi` itself,
53//! without calling a wrapper, must keep the library by other means, such as the linker
54//! arguments `tvm-tirx-config --libs compiler` prints.
55//!
56//! ```no_run
57//! use tvm_tirx::target::Target;
58//!
59//! let target = Target::new("llvm")?;
60//! assert_eq!(target.kind()?.name()?.as_str(), "llvm");
61//! # Ok::<(), tvm_tirx::tvm_ffi::Error>(())
62//! ```
63//!
64//! A handle such as [`ir::Expr`] is a reference-counted pointer to a native object, so cloning it
65//! does not copy the IR, and its `*Obj` type ([`ir::ExprObj`]) is the object. Each binding says
66//! whether its layout is *complete* or *opaque*. A complete `*Obj` reproduces the native object
67//! byte for byte and exposes its reflected fields directly. The layout of an opaque one cannot be
68//! rebuilt from the reflection (it has unreflected members, or no layout metadata), so its fields
69//! are read through fallible getters over the C ABI. Use [`tvm_ffi::ObjectRefCast`] for checked
70//! casts between handles.
71//!
72//! A complete object can also be allocated from Rust. Its `new` takes every field and stores it
73//! as given, without the checks, defaults or derived fields of the native constructor. Where the
74//! native constructor does more than that (`ir::prim::Add` checks its operand types,
75//! `tirx::Function` derives its type from the signature), `new` is reserved for a constructor with
76//! those semantics, and the allocation of the fields as given is `from_fields`. The IR
77//! constructors are written in Rust after the C++ ones, with the same checks, defaults, derived
78//! fields and errors; they call into C++ only for the nodes C++ shares (`UnknownLoc`,
79//! `MissingType` and the `PrimType` of each dtype, fetched once per thread), for the hooks an
80//! operator or type registers (such as `FInferType`), and for printing in an error message.
81//! A constructor returns a `Result` when its C++ counterpart can throw, and the node itself
82//! otherwise: [`ir::Var::new`] or [`ir::UnknownLoc::new`] cannot fail, because the native calls
83//! they make are to functions the linked library registers, and a failure there is a mismatch
84//! between the crate and the library, which panics.
85//!
86//! The common types and constants have the short constructors C++ has: [`ir::PrimType::int`]
87//! and its siblings for `PrimType::Int(32)`, [`ir::IntImm::int32`], [`ir::IntImm::bool`] and
88//! [`ir::FloatImm::float32`] for the constants, [`ir::prim::make_const`] for a constant of any
89//! type, and the conversions of `i32`, `i64`, `bool`, `f32` and `f64` into an [`ir::Expr`] that
90//! C++ makes implicitly. [`ir::dtype`] spells the `DLDataType` of each (`dtype::int(32)`) without
91//! parsing a string.
92//! The unknown location is [`ir::UNKNOWN_LOC`] as a constructor argument and
93//! [`ir::Location::unknown`] as a value.
94//!
95//! The operators are written in Rust too, after `src/ir/prim/op.cc`: [`ir::prim::op::add`] and
96//! its siblings match their operand types and fold constants as C++ `add` does, and the math
97//! functions ([`ir::prim::op::floor`], [`ir::prim::op::exp`], ...) build the same calls. They
98//! take expressions or literals typed as C++ types them and build at the unknown location (the
99//! `_at` variants take one), and an [`ir::prim::op::ExprResult`] gives them operator syntax:
100//! `floordiv(&x + 1, 4)?` is the C++ `floordiv(x + 1, 4)`. An `ExprResult` passes into any function or
101//! constructor that takes an [`ir::IntoExpr`], as any expression does.
102//!
103//! Operators and types are defined from Rust in a [`tvm_ffi::static_init_block!`], as C++ defines
104//! them in a `TVM_FFI_STATIC_INIT_BLOCK`. An operator is an [`ir::OpDef`] chain, the C++ `OpDef`,
105//! with the signature ([`ir::sig`], whose descriptors generate the validator), the attributes, by
106//! the keys of [`ir::op_attr`] and [`tirx::op_attr`], and the type inference, validator and
107//! region hooks as Rust functions, which C++ calls natively; a type, written outside the block as
108//! any other ([Defining a type in Rust](#defining-a-type-in-rust)), is registered by
109//! [`ir::register_type`]:
110//!
111//! ```no_run
112//! use tvm_tirx::ir::op_attr::CALL_EFFECT_KIND;
113//! use tvm_tirx::ir::sig::{self, IntExpr};
114//! use tvm_tirx::ir::{register_type, CallEffectKind, CallObj, Op, OpDef, Type};
115//! use tvm_tirx::tvm_ffi::{self, Result};
116//! # use tvm_tirx::ir::TypeObj;
117//! # use tvm_tirx::tvm_ffi::{def_object_ref, rs_object, ObjectRefCore};
118//! # #[rs_object("my_ext.PairType", final)]
119//! # pub struct PairTypeObj { base: TypeObj, pub first: Type, pub second: Type }
120//! # def_object_ref!(pub PairType, Type, PairTypeObj);
121//!
122//! fn index_type(call: &CallObj) -> Result<Type> {
123//!     Ok(call.args.get(0)?.ty.clone())
124//! }
125//!
126//! tvm_ffi::static_init_block! {
127//!     OpDef::new("my_ext.clamp", "Clamp an index to the range `[0, bound)`.")
128//!         .signature((
129//!             sig::arg::<IntExpr>("index", "The index."),
130//!             sig::arg::<IntExpr>("bound", "The exclusive upper bound."),
131//!         ))
132//!         .set_infer_type(index_type)
133//!         .set_attr(CALL_EFFECT_KIND, CallEffectKind::Pure);
134//!     register_type::<PairType>()?;
135//! }
136//!
137//! let clamp = Op::get("my_ext.clamp")?;
138//! # Ok::<(), tvm_ffi::Error>(())
139//! ```
140//!
141//! A block runs when its program or library loads, as a C++ one does, wherever in it the block
142//! is. [`ir::Op::get`] then returns the operator, as C++ `Op::Get` does: the registry keeps one
143//! object per name, so `call.op.same_as(&clamp)` tests whether a call is to it. Every library
144//! built on the crate exports [`tvm_ffi::run_static_init_blocks`], which reports the errors of the
145//! blocks that failed, as the TVM FFI function `tirx_register_ir`.
146//!
147//! # The library Python loads
148//!
149//! The crate is also built as a shared library, which the TIRx build installs as `libtvm_tirx_rust`
150//! next to `libtvm_tirx_compiler` when it finds a cargo as new as the crate's `rust-version`
151//! (`TVM_TIRX_USE_RUST`, `AUTO` by default). `import tvm_tirx` loads it through the backend
152//! autoload (`tvm_tirx.backend.rust`), which registers the operators and types the crate defines by
153//! the time the import returns, as the C++ ones are, and calls `tirx_register_ir` to raise the
154//! error of a block that failed. Python uses the operators as it uses the C++ ones: `Op.get` finds
155//! them, a `Call` built in Python runs their hooks, and the TVMScript printer prints their calls.
156//! Completing an operator, when its [`ir::OpDef`] chain ends, or a type with [`ir::register_type`]
157//! requests API exposure through the `ir.expose_op` or `ir.expose_type` FFI receiver. Python
158//! installs these receivers before loading native libraries and publishes the selected definitions
159//! to registered destinations, including destinations initialized later. Op API destinations
160//! construct raw calls; script destinations add builder behavior. Type destinations publish
161//! constructors, such as `T.<Name>` for `tirx.<Name>Type`. Handwritten Python bindings take
162//! precedence in each destination. Without receivers, native registration proceeds without API
163//! exposure.
164//!
165//! A library of operators and types of its own, a `cdylib` built on the crate as
166//! `examples/define_ir.rs` is, registers them when Python loads it, by `tvm_ffi.load_module` or
167//! `ctypes`, as a C++ library does, and stays loaded for the process. Each library links its own
168//! copy of the crates it is built from, so several libraries can have the same block, as those of a
169//! crate they share: the first library that runs it registers what it defines and the others skip
170//! it, so the libraries load together. A crate that a library depends on but never names is not
171//! linked into it, nor are its blocks: name it, as `use my_ops as _;` does.
172//!
173//! # Defining a type in Rust
174//!
175//! [`tvm_ffi::rs_object`] defines a new IR type, a type of expressions as [`ir::PrimType`] and
176//! [`ir::TupleType`] are, from its object struct, whose first field `base` is the [`ir::TypeObj`]
177//! it extends, which holds the location. It registers the type under `ir.Type` with the
178//! reflection of every other field, so that the C++ structural equality and hashing, deep copy,
179//! `repr`, the TVMScript printer and Python see the fields as they see a C++ type's.
180//! [`tvm_ffi::def_object_ref`] defines the reference, which converts into [`ir::Type`]. The
181//! object's `new` takes the `TypeObj`, then the fields in order:
182//!
183//! ```no_run
184//! use tvm_tirx::ir::{Location, PrimType, Type, TypeObj};
185//! use tvm_tirx::tvm_ffi::{self, def_object_ref, rs_object, ObjectRefCore};
186//!
187//! /// The type of a pair of values.
188//! #[rs_object("my_ext.PairType", final)]
189//! pub struct PairTypeObj {
190//!     base: TypeObj,
191//!     pub first: Type,
192//!     pub second: Type,
193//!     /// Not part of structural equality or hashing.
194//!     #[reflect(seq_hash_ignore)]
195//!     pub note: tvm_ffi::String,
196//! }
197//!
198//! def_object_ref!(pub PairType, Type, PairTypeObj);
199//!
200//! impl PairType {
201//!     pub fn new(first: impl Into<Type>, second: impl Into<Type>) -> Self {
202//!         PairTypeObj::new(TypeObj::new(Location::unknown()), first, second, "").into()
203//!     }
204//! }
205//!
206//! fn main() {
207//!     let pair = PairType::new(PrimType::int(32), PrimType::float(32));
208//!     let ty: Type = pair.into(); // an `ir.Type` that C++ sees as `my_ext.PairType`
209//!     assert!(ty.downcast_ref::<PairTypeObj>().is_some());
210//! }
211//! ```
212//!
213//! The generated code names `tvm_ffi`, which `use tvm_tirx::tvm_ffi` brings into scope in a crate
214//! that depends only on `tvm-tirx`. The parent's object must have a public `new` and implement
215//! `ShallowCopy` and `UnsafeInit`; the bindings generate them for a complete type that is not
216//! final, as `ir.Type`. Registered by [`ir::register_type`] in a [`tvm_ffi::static_init_block!`],
217//! with the operators, the type is also constructed by Python from its fields and parsed by
218//! TVMScript, as a C++ type.
219//!
220//! # Generated and hand-written code
221//!
222//! The code between a `// tvm-ffi-stubgen(begin)` and its `// tvm-ffi-stubgen(end)` is generated
223//! and rewritten in place. Everything outside the blocks is hand-written, including the
224//! `tvm-ffi-stubgen(...)` directives that steer the generator.
225//!
226//! The blocks of the objects a Python module defines are in the Rust file at the same path:
227//! `python/tvm_tirx/ir/prim/expr.py` is `src/ir/prim/expr.rs`. `target` and `runtime`, whose
228//! objects come from a single Python module each, are one file. A type is in the module where
229//! Python defines it, which is not always its type-key namespace: `tirx.cuda.*` is in
230//! [`backend::cuda`] and `tirx.tensor.*` in [`tirx::tile`]. A type Python has no class for is next
231//! to the types it belongs to, and its file says so. A parent module re-exports its files, so
232//! [`ir::Expr`] names `ir::expr::Expr`. It also holds the `prefix` directive of its namespace: an
233//! object registered later that no file has a block for yet is generated there, to be moved to
234//! its file.
235//!
236//! Regenerate from the repository root after rebuilding `libtvm_tirx_compiler` (add `--check` to
237//! only report stale blocks):
238//!
239//! ```bash
240//! tvm-ffi-stubgen rust/src --target rust --dlls build/lib/libtvm_tirx_compiler.so
241//! ```
242//!
243//! `tvm-ffi-stubgen` comes with the `tvm_ffi` Python package, which must be the one of
244//! `3rdparty/tvm-ffi`: the blocks are what its generator emits. The blocks are formatted as
245//! rustfmt formats them, so `cargo fmt --check` and `tvm-ffi-stubgen --check` agree.
246//!
247//! # Tests
248//!
249//! Build `libtvm_tirx_compiler` first. The build scripts need `tvm-ffi-config` and
250//! `tvm-tirx-config` on `PATH`, which `uv run` provides from the `.venv` after the editable
251//! install, where `tvm-tirx-config --libdir` is `build/lib`:
252//!
253//! ```bash
254//! uv run --no-sync cargo test --manifest-path rust/Cargo.toml
255//! ```
256//!
257//! Set `TVM_TIRX_LIBRARY_PATH` to the directory of another `libtvm_tirx_compiler` to build and
258//! test against that one; `tvm-tirx-config` puts it first.
259//!
260//! The tests are laid out like the modules. Each top-level module is one test binary,
261//! `tests/<module>/main.rs`, and the tests of `src/<path>.rs` are in `tests/<path>.rs`:
262//! `tests/tirx/transform/function_pass.rs` tests `src/tirx/transform/function_pass.rs`. Run the
263//! tests of one module with `--test <module>`, such as `--test tirx`. `tests/common/` holds the
264//! helpers the binaries share.

266// The crate reaches `libtvm_tirx_compiler` through the FFI registry, so a linker that drops
267// unreferenced libraries (`--as-needed`) would drop the library the build script links, and its
268// registrations would never run. Each TIRx shared library exports a `<library>_link_anchor`
269// function that does nothing, defined in the `link_anchor.cc` of its sources (for the compiler,
270// `src/ir/link_anchor.cc`) and declared by whoever references it. The static below holds the
271// anchor's address: a relocation against the symbol in the object of this module, which costs
272// nothing at run time and is what makes the linker keep the library.
273//
274// A program pulls in only the objects of the crate it references, so the static keeps the
275// library only when the object of this module is pulled. It is, because the objects of the crate
276// reference one another densely and `sym::analyzer` references `ExitOnDrop::new` below. The test
277// binaries rely on the same mechanism and fail at their first registry lookup if that changes. A
278// program that uses the registry only through `tvm_ffi` itself, without calling a wrapper, must
279// keep the library by other means, such as the linker arguments `tvm-tirx-config --libs compiler`
280// prints.
281extern "C" {
282    fn tvm_tirx_compiler_link_anchor() -> i32;
283}

288/// Makes a scope guard neither `Send` nor `Sync`: the native scopes keep their state per thread,
289/// or in an object that is not synchronized, so a scope must end on the thread that opened it.
290pub(crate) type ThreadBound = std::marker::PhantomData<*const ()>;
291
292/// Calls a native exit function when dropped: the end of a scope a native enter function opened.
293pub(crate) struct ExitOnDrop(tvm_ffi::Function, ThreadBound);
294
295impl ExitOnDrop {
296    pub(crate) fn new(exit: tvm_ffi::Function) -> Self {
297        Self(exit, ThreadBound::default())
298    }
299}
300
301impl Drop for ExitOnDrop {
302    fn drop(&mut self) {
303        // A destructor cannot report the error, and the native exit functions do not fail.
304        let _ = self.0.call_packed(&[]);
305    }
306}
