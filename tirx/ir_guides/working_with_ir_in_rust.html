Working with IR in Rust#

The IR objects we have used so far in Python are TVM-FFI objects, and the same objects are available in Rust through the tvm-tirx crate. A Rust function can receive a function written in TVMScript, read and rewrite it, and return the result to Python. Nothing is converted or copied along the way: Python and Rust hold references to the same native objects.

This chapter assumes the concepts of the earlier chapters and shows their Rust form:

  • Accessing and creating IR nodes: read fields, branch on node types, and build new nodes.

  • Structural utilities: walk, map, and compare programs, with callbacks selected by their Rust parameter types.

  • Visitors and mutators: keep state across callbacks and control the traversal, with #[dispatch] structs and VisitCallbacks.

Note

The runnable code in this chapter is under examples/ir_guides in the repository.

Setting Up#

Throughout this chapter, we use the add_one function from Quick Start:

from tvm_tirx.script import tirx as T

n = T.dynamic("n")


@T.function
def add_one(A: T.Tensor((n,), T.float32), B: T.Tensor((n,), T.float32)):
    for i in range(n):
        B[i] = A[i] + 1

The examples are packaged as tirx_ir_guide_examples under examples/ir_guides. When cargo is available, installing the package builds the Rust crate in rust/ into a library; CMakeLists.txt and pyproject.toml in the same directory show how. The crate uses the bindings from this checkout, so install TIRx from the same source tree. We install without build isolation to build against that installation instead of fetching one from PyPI:

pip install scikit-build-core
pip install --no-build-isolation -e examples/ir_guides

Each example is a Rust function that takes add_one as its argument. A static_init_block! at the end of the crate registers each one as a global function under tirx_ir_guide_examples.rust:

tvm_ffi::Function::register_global_typed(
    "tirx_ir_guide_examples.rust.inspect",
    inspect,
    "Read the fields of a function.",
)?;

The package’s tirx_ir_guide_examples.rust module loads the library and exposes these functions, so Python calls them by name:

import tirx_ir_guide_examples.rust

tirx_ir_guide_examples.rust.inspect(add_one)

The driver working_with_ir_in_rust.py calls each example this way and prints the result.

Accessing and Creating IR Nodes#

Every IR node has two Rust types: a handle such as For, a reference-counted pointer that is cheap to clone, and the object it points to, such as ForObj, which holds the fields. A handle dereferences to its object, so we read fields as ordinary struct fields.

Let’s read add_one from its parameters down to the store in its loop. The statements of a body are general Stmt handles, and match_any! branches on their actual node type, as match does on an enum:

fn inspect(func: Function) -> Result<tvm_ffi::String> {
    let mut lines = Vec::new();
    for param in func.params.iter() {
        lines.push(format!("param {}", param.name.as_str()));
    }
    let body = &func.body;
    for stmt in body.seq.iter() {
        describe(stmt, "", &mut lines)?;
    }
    Ok(lines.join("\n").into())
}

fn describe(stmt: Stmt, indent: &str, lines: &mut Vec<String>) -> Result<()> {
    match_any! {
        stmt {
            For(loop_) => {
                let (var, end) = (loop_.var.name.as_str(), script(&loop_.end)?);
                lines.push(format!("{indent}loop over {var} up to {}", end.as_str()));
                for child in loop_.body.seq.iter() {
                    describe(child, &format!("{indent}  "), lines)?;
                }
            },
            TensorStore(store) => {
                let (dest, value) = (script(&store.dest)?, script(&store.value)?);
                lines.push(format!("{indent}store to {}: {}", dest.as_str(), value.as_str()));
            },
            _ => lines.push(format!("{indent}other statement")),
        }
    }
    Ok(())
}

The output is:

param A
param B
loop over i up to n
  store to B: A[i] + T.float32(1.0)

Each arm names a handle type and binds the matching node to it; the arms are tried in order, and _ takes everything else. Fields have the types we know from Python: params is an Array<Var>, and the body of a loop is a SeqStmt whose seq holds its statements. script prints any node as TVMScript.

Note

A function’s body is always a SeqStmt. get on an array returns an error for an index out of range, and ? passes it on.

To create a node, we call the constructor of its handle type, such as TensorStore::new. ex wraps an expression so that the usual Rust operators build IR; constructors accept the result directly. Let’s build a store that writes twice the value of the store in add_one:

fn double_store(func: Function) -> Result<TensorStore> {
    let body = &func.body;
    let loop_: For = body.seq.get(0)?.try_cast()?;
    let store: TensorStore = loop_.body.seq.get(0)?.try_cast()?;
    let doubled = ex(&store.value) * 2;
    TensorStore::new(&store.dest, store.indices.iter(), doubled, UNKNOWN_LOC)
}

The output is:

n = T.dynamic("n", dtype="int32")
B = T.Var("B", T.Tensor((n,), T.float32))
i = T.dynamic("i", dtype="int32")
A = T.Var("A", T.Tensor((n,), T.float32))
B[i] = (A[i] + T.float32(1.0)) * T.float32(2.0)

The new store reuses the destination and indices of the old one, so the printer declares them as free variables first. Constructing nodes creates new objects; add_one itself is not modified. Here try_cast downcasts to a single known type instead of branching.

Structural Utilities#

The structural utilities are part of TVM-FFI, and the tvm_ffi crate, re-exported as tvm_tirx::tvm_ffi, provides them in Rust: structural_walk, structural_map, structural_visit, and structural_mutate. They run on the same structural hooks as in Python, so they reach the same nodes and keep definitions and uses consistent in the same way. What changes is the Rust form of each piece:

order="pre" or the default post-order

Structural Walk#

As in Python, a walk calls our callback on each node of the type it asks for. Let’s find the tensors that add_one writes:

fn written_tensors(func: Function) -> Result<Strings> {
    let mut writes = Vec::new();
    let on_store = |store: TensorStore| -> Result<WalkResult> {
        let dest: Var = store.dest.clone().try_cast()?;
        writes.push(dest.name.clone());
        Ok(WalkResult::Advance)
    };
    tvm_ffi::structural_walk(&func, on_store, WalkOrder::PostOrder)?;
    Ok(writes.into_iter().collect())
}

The output is:

['B']

on_store takes a TensorStore, so the walk calls it only on stores. Strings is our alias for Array<tvm_ffi::String>, which Python receives as a list of strings.

WalkResult::Advance continues into the node’s children, Skip does not descend into them, and Interrupt stops the whole walk.

The parameter list of a callback decides what it receives:

Callback

Receives

|store: TensorStore|

Each write, as a handle.

|store: &TensorStoreObj|

Each write, as a borrowed object, without changing its reference count.

|value: &StructuralView|

Every value the walk reaches.

|var: Var, kind: DefRegionKind|

Each variable, with its definition region kind.

(on_loop, on_store)

A tuple of callbacks, tried in order; only the first one whose type matches a node runs. Tuples hold up to 12 callbacks and can be nested.

WalkResult::interrupt_with stops the walk and returns a value, which lets a walk search for a node:

fn first_write(func: Function) -> Result<Option<TensorStore>> {
    let find_write = |store: TensorStore| WalkResult::interrupt_with(store);
    let found = tvm_ffi::structural_walk(&func, find_write, WalkOrder::PostOrder)?;
    match found {
        Some(interrupt) => Ok(Some(interrupt.value.try_into()?)),
        None => Ok(None),
    }
}

Python prints the dest.name of the store it receives. The output is:

B

structural_walk returns Ok(Some(interrupt)) when a callback stops it, with the payload in interrupt.value, and Ok(None) otherwise.

Definitions and Uses#

A callback receives the definition region kind when it takes a DefRegionKind as its last parameter. This walk lists the definition sites of add_one:

fn definitions(func: Function) -> Result<Strings> {
    let mut sites = Vec::new();
    let show_definition = |var: Var, kind: DefRegionKind| {
        if kind != DefRegionKind::None {
            sites.push(format!("{} {:?}", var.name.as_str(), kind));
        }
        WalkResult::Advance
    };
    tvm_ffi::structural_walk(&func, show_definition, WalkOrder::PreOrder)?;
    Ok(sites.iter().map(tvm_ffi::String::from).collect())
}

The output is:

A Pattern
n Pattern
B Pattern
n Pattern
i Simple

The kinds are the ones we saw in Python, under Rust names: DefRegionKind::None for a use site, Pattern for DEF_PATTERN, and Simple for DEF_SIMPLE. structural_map callbacks take the same trailing parameter.

Structural Map#

A map callback returns the replacement for its node. Let’s specialize add_one for n = 128, with n passed in from Python:

fn specialize(func: Function, n: Var, value: i64) -> Result<Function> {
    let specialize_var = |var: Var| -> Result<Expr> {
        if var.same_as(&n) {
            let ty: PrimType = var.ty.clone().try_cast()?;
            return make_const(ty, value);
        }
        Ok(var.into())
    };
    tvm_ffi::structural_map(func, specialize_var, WalkOrder::PostOrder)?.try_into()
}

The output is:

from __future__ import annotations

# from tvm_tirx.script import tirx as T

@T.function
def add_one(A: T.Tensor((128,), T.float32), B: T.Tensor((128,), T.float32)):
    for i in range(128):
        B[i] = A[i] + T.float32(1.0)

This is the same result as in Python. make_const builds the constant 128 with the type of n, and every other variable is returned as it is. structural_map takes ownership of the handle we pass and returns the new root as an Any; Python still holds add_one, which is unchanged.

Structural Equality#

The crate has no Rust function for structural equality yet, so we call the global function that Python’s structural_equal uses, ffi.StructuralEqual, with its four arguments: the two values, map_free_vars, and skip_tensor_content. Let’s specialize add_one twice and compare the results:

fn compare_specialized(func: Function, n: Var) -> Result<Array<bool>> {
    let first = specialize(func.clone(), n.clone(), 128)?;
    let second = specialize(func, n, 128)?;
    let (map_free_vars, skip_tensor_content) = (false, false);
    let equal: bool = tvm_ffi::Function::get_global("ffi.StructuralEqual")?
        .call_tuple((&first, &second, map_free_vars, skip_tensor_content))?
        .try_into()?;
    Ok([first.same_as(&second), equal].into_iter().collect())
}

The output is:

[False, True]

The two functions are different objects, so same_as is false, but they are structurally equal.

Visitors and Mutators in Rust#

Rust has no separate layer of visitor and mutator classes. Stateful and typed traversals use the same four structural utilities, and the crate provides two conveniences to build them: #[dispatch] turns the methods of a struct into typed callbacks, and VisitCallbacks and MutateCallbacks attach state to a tuple of callbacks.

Typed Dispatch on a Struct#

The closures in a callback tuple cannot borrow the same state mutably at the same time, so callbacks that share state are written as methods instead. #[dispatch(walk)] on an impl block turns its walk_* methods into callbacks: each method receives the nodes of its parameter type, and the methods are tried in source order. The struct holds the state. Let’s record the loops and writes of add_one in the order the walk reaches them:

#[derive(Default)]
struct StatementTrace {
    events: Vec<String>,
}

#[dispatch(walk)]
impl StatementTrace {
    fn walk_for(&mut self, loop_: &ForObj) -> WalkResult {
        self.events.push(format!("loop {}", loop_.var.name.as_str()));
        WalkResult::Advance
    }

    fn walk_store(&mut self, store: &TensorStoreObj) -> Result<WalkResult> {
        self.events.push(format!("write {}", script(&store.dest)?.as_str()));
        Ok(WalkResult::Advance)
    }
}

fn trace_statements(func: Function, pre_order: bool) -> Result<Strings> {
    let order = if pre_order { WalkOrder::PreOrder } else { WalkOrder::PostOrder };
    let mut trace = StatementTrace::default();
    tvm_ffi::structural_walk(&func, &mut trace, order)?;
    Ok(trace.events.iter().map(tvm_ffi::String::from).collect())
}

Called with pre_order true and then false, the output is:

['loop i', 'write B']
['write B', 'loop i']

Pre-order reports the loop before the write inside it, and post-order the reverse. A method may also take a trailing DefRegionKind, as a closure can. #[dispatch(map)], #[dispatch(visit)], and #[dispatch(mutate)] work the same way for map_*, visit_*, and mutate_* methods.

Visit and Mutate#

A visit or mutate callback takes control of its node’s children, as in Python. Let’s record the loops around each write. With VisitCallbacks, each callback receives the node and a VisitContext, which holds the shared state:

#[derive(Default)]
struct LoopNest {
    loops: Vec<String>,
    writes: Vec<String>,
}

fn visit_for(
    loop_: &ForObj,
    visitor: &mut VisitContext<'_, LoopNest>,
) -> Result<Option<VisitInterrupt>> {
    visitor.state_mut().loops.push(loop_.var.name.as_str().to_owned());
    let result = visitor.visit_children()?;
    visitor.state_mut().loops.pop();
    Ok(result)
}

fn visit_store(store: &TensorStoreObj, visitor: &mut VisitContext<'_, LoopNest>) -> Result<()> {
    let loops = visitor.state().loops.join(", ");
    let write = format!("{} inside [{}]", script(&store.dest)?.as_str(), loops);
    visitor.state_mut().writes.push(write);
    Ok(())
}

fn loops_around_writes(func: Function) -> Result<Strings> {
    let mut visitor = VisitCallbacks::new(LoopNest::default(), (visit_for, visit_store));
    tvm_ffi::structural_visit(&func, &mut visitor)?;
    let state = visitor.into_state();
    assert!(state.loops.is_empty());
    Ok(state.writes.iter().map(tvm_ffi::String::from).collect())
}

The output is:

['B inside [i]']

visit_for pushes the loop variable, lets visit_children visit the loop’s children with their usual traversal, then pops the variable. It returns the result of visit_children, so that an interrupt from a child reaches the caller. The context also provides visit for a selected child and def_region_kind for the current node.

For the mutation we use the struct form instead; either form works for both visits and mutations. A #[dispatch(mutate)] method that takes a trailing &mut Mutator gets the mutation counterpart of VisitContext, with default_mutate for the children and def_region_kind(). Let’s reverse the loop by replacing each use of i with n - 1 - i, built with ex as before:

#[derive(Default)]
struct ReverseLoops {
    reversed_index: HashMap<ObjectIdentity, Expr>,
}

#[dispatch(mutate)]
impl ReverseLoops {
    fn mutate_for(&mut self, loop_: For, mutator: &mut Mutator) -> Result<Any> {
        let index = (ex(&loop_.end) - 1 - &loop_.var).expr()?;
        self.reversed_index.insert(ObjectIdentity::of(&loop_.var), index);
        mutator.default_mutate(self, &loop_)
    }

    fn mutate_var(&mut self, var: Var, mutator: &mut Mutator) -> Expr {
        let is_use = mutator.def_region_kind() == DefRegionKind::None;
        match self.reversed_index.get(&ObjectIdentity::of(&var)) {
            Some(index) if is_use => index.clone(),
            _ => var.into(),
        }
    }
}

fn reverse_loops(func: Function) -> Result<Function> {
    tvm_ffi::structural_mutate(func, ReverseLoops::default())?.try_into()
}

The output is:

from __future__ import annotations

# from tvm_tirx.script import tirx as T

@T.function
def add_one[n](A: T.Tensor((n,), T.float32), B: T.Tensor((n,), T.float32)):
    for i in range(n):
        B[n - 1 - i] = A[n - 1 - i] + T.float32(1.0)

mutate_for records the replacement, then default_mutate rewrites the loop’s children through the same struct, so mutate_var sees the replacement before any use of i.

Note

mutate_var replaces i only where def_region_kind() is None, so the loop’s own i stays a variable. ObjectIdentity keys the map by object identity, as the Python version keys its dictionary by variable.

Note

TIRx also has traversals that track the facts valid at each node, such as loop ranges and branch conditions. In Rust they are StructuralVisitorWithConstraintContext and StructuralMutatorWithConstraintContext; constraints() returns the current facts.

With fields, typed callbacks, and the structural utilities, a Rust function works with the same IR that Python builds and prints, so an analysis or a transformation can move between the two languages one function at a time.
