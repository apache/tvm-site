Working with IR in C++#

The IR objects we have used from Python are TVM-FFI objects implemented in C++. A C++ function can receive add_one from Python, inspect or rewrite it, and hand the result back, with no conversion in between. This lets us move a hot analysis or a large transformation to C++ while keeping the rest of the workflow in Python.

This chapter assumes the concepts of the earlier chapters and shows their C++ form:

  • Accessing and creating IR nodes: read fields, check node types, and build new nodes.

  • Structural utilities: walk, map, and compare programs, with callbacks selected by their parameter types.

  • Visitor and mutator classes: C++ classes with one hook per node kind, for passes that customize many kinds of node.

Note

The runnable code in this chapter is under examples/ir_guides in the repository.

Setting Up#

Throughout this chapter, we use the add_one function from Quick Start:

from tvm_tirx.script import tirx as T

n = T.dynamic("n")


@T.function
def add_one(A: T.Tensor((n,), T.float32), B: T.Tensor((n,), T.float32)):
    for i in range(n):
        B[i] = A[i] + 1

The examples are packaged as tirx_ir_guide_examples under examples/ir_guides. Installing the package builds the C++ source, cpp/working_with_ir.cc, into a library; CMakeLists.txt and pyproject.toml in the same directory show how. Install TIRx from the same source tree to keep the IR APIs aligned. We install without build isolation to build against that installation instead of fetching one from PyPI:

pip install scikit-build-core
pip install --no-build-isolation -e examples/ir_guides

Each example is a C++ function that takes add_one as its argument. A TVM_FFI_STATIC_INIT_BLOCK at the end of the source registers each one as a global function under tirx_ir_guide_examples.cpp:

refl::GlobalDef()
    .def("tirx_ir_guide_examples.cpp.inspect", Inspect)

The package’s tirx_ir_guide_examples.cpp module loads the library and exposes these functions, so Python calls them by name:

import tirx_ir_guide_examples.cpp

tirx_ir_guide_examples.cpp.inspect(add_one)

The driver working_with_ir_in_cpp.py calls each example this way and prints the result.

IR classes live in the tvm namespace, TIRx-specific ones such as tvm::tirx::Function in tvm::tirx, and the TVM-FFI classes in tvm::ffi. The examples start with using namespace tvm;, so these appear as Var, tirx::Function, and ffi::StructuralWalk.

Each IR node has two C++ classes. The node class, named with an Obj suffix such as tvm::ForObj, holds the fields. The reference class without the suffix, such as tvm::For, is a reference-counted handle to a node, and is what functions take and return. The -> operator on a reference reaches the node’s fields.

Let’s read add_one from its parameters down to the store in its loop:

ffi::String Inspect(const tirx::Function& func) {
  std::ostringstream os;
  for (const Var& param : func->params) {
    os << "param " << param->name << "\n";
  }
  SeqStmt body = func->body;
  if (const ForObj* loop = body[0].as<ForObj>()) {
    os << "loop over " << loop->var.as<VarObj>()->name << " up to " << loop->end << "\n";
    if (const TensorStoreObj* store = loop->body[0].as<TensorStoreObj>()) {
      os << "  store to " << store->dest.as<VarObj>()->name << ": " << store->value;
    }
  }
  return os.str();
}

The output is:

param A
param B
loop over i up to n
  store to B: A[i] + T.float32(1.0)

Fields have the types we know from Python, and writing an expression to a stream prints it in TVMScript. The elements of a SeqStmt are general Stmt references, so we check the actual node type before reading a loop or a store. ObjectRef::as and its relatives offer three forms:

Call

Returns

stmt.as<ForObj>()

A pointer to the node, or nullptr if it is not a loop.

stmt.as<For>()

A std::optional<For> reference.

stmt.as_or_throw<For>()

The For reference, or raises an error.

Note

A function’s body is always a SeqStmt. The loop variable is stored as a PrimVar, which views a Var as a PrimExpr, so we read its name through as<VarObj>().

To create a node, we call the constructor of its reference class, and arithmetic operators on PrimExpr build new expressions. Let’s build a store that writes twice the value of the store in add_one:

TensorStore DoubleStore(const tirx::Function& func) {
  For loop = func->body[0].as_or_throw<For>();
  TensorStore store = loop->body[0].as_or_throw<TensorStore>();
  PrimExpr doubled = store->value * 2;
  return TensorStore(store->dest, store->indices, doubled);
}

The output is:

n = T.dynamic("n", dtype="int32")
B = T.Var("B", T.Tensor((n,), T.float32))
i = T.dynamic("i", dtype="int32")
A = T.Var("A", T.Tensor((n,), T.float32))
B[i] = (A[i] + T.float32(1.0)) * T.float32(2.0)

The new store reuses the destination and indices of the old one, so the printer declares them as free variables first. store->value * 2 turns the literal into a constant of the value’s type, T.float32(2.0). Constructing nodes creates new objects; add_one itself is not modified.

Structural Walk#

As in Python, a walk calls our callback on each node of the type it asks for. To find the tensors that add_one writes, the callback takes a const TensorStore&:

ffi::Array<ffi::String> TensorsWritten(const tirx::Function& func) {
  ffi::Array<ffi::String> writes;
  ffi::StructuralWalk<ffi::WalkOrder::kPostOrder>(
      func, [&](const TensorStore& store) -> ffi::Expected<ffi::WalkResult> {
        writes.push_back(store->dest.as<VarObj>()->name);
        return ffi::WalkResult::Advance();
      });
  return writes;
}

The output is:

['B']

Only the store reaches the callback, because its parameter is const TensorStore&.

A walk callback returns an ffi::Expected<ffi::WalkResult>. WalkResult::Advance() continues the walk, WalkResult::Skip() skips the node’s children in pre-order, and WalkResult::Interrupt(...) stops the walk.

To handle several node kinds in one walk, we pass one callback per kind as extra arguments. They are tried in declaration order, and only the first one whose parameter type matches a node runs; a node that matches none is still traversed but not reported. This walk records the loops and stores in pre-order:

ffi::Array<ffi::String> TraceStatements(const tirx::Function& func) {
  ffi::Array<ffi::String> trace;
  ffi::StructuralWalk<ffi::WalkOrder::kPreOrder>(
      func,
      [&](const For& loop) -> ffi::Expected<ffi::WalkResult> {
        trace.push_back("loop " + loop->var.as<VarObj>()->name);
        return ffi::WalkResult::Advance();
      },
      [&](const TensorStore& store) -> ffi::Expected<ffi::WalkResult> {
        trace.push_back("store " + store->dest.as<VarObj>()->name);
        return ffi::WalkResult::Advance();
      });
  return trace;
}

The output is:

['loop i', 'store B']

The loop and the store each reach their own callback, and pre-order reports the loop before the store inside it. Matching follows the class hierarchy, so a callback that takes a base class, such as const Stmt&, would also take loops and stores that no earlier callback claims.

To stop at the first match and return it, a callback wraps the node in an ffi::VisitInterrupt. StructuralWalk returns that interrupt, or std::nullopt if the walk finished without one:

ffi::Optional<TensorStore> FindWrite(const tirx::Function& func) {
  ffi::Optional<ffi::VisitInterrupt> found = ffi::StructuralWalk<ffi::WalkOrder::kPreOrder>(
      func, [](const TensorStore& store) -> ffi::Expected<ffi::WalkResult> {
        return ffi::WalkResult::Interrupt(ffi::VisitInterrupt(store));
      });
  if (!found.has_value()) return std::nullopt;
  return found.value()->value.cast<TensorStore>();
}

The output is:

B

The interrupt’s value field carries the payload as an ffi::Any, and cast<TensorStore>() converts it back to a store.

Definitions and Uses#

A callback receives the definition region kind of each site when it takes a TVMFFIDefRegionKind as its last parameter. The kinds match Python’s: kTVMFFIDefRegionKindNone for a use, kTVMFFIDefRegionKindSimple for DEF_SIMPLE, and kTVMFFIDefRegionKindPattern for DEF_PATTERN. Let’s list the definition sites in add_one:

ffi::Array<ffi::String> Definitions(const tirx::Function& func) {
  ffi::Array<ffi::String> sites;
  ffi::StructuralWalk<ffi::WalkOrder::kPreOrder>(
      func, [&](const Var& var, TVMFFIDefRegionKind kind) -> ffi::Expected<ffi::WalkResult> {
        if (kind == kTVMFFIDefRegionKindSimple) {
          sites.push_back(var->name + " simple");
        } else if (kind == kTVMFFIDefRegionKindPattern) {
          sites.push_back(var->name + " pattern");
        }
        return ffi::WalkResult::Advance();
      });
  return sites;
}

The output is:

A pattern
n pattern
B pattern
n pattern
i simple

These are the same sites as in Python: the parameters define A, B, and n by pattern, and the loop defines i.

Structural Map#

ffi::StructuralMap takes the same callbacks, but each one returns a replacement for its node. Let’s specialize add_one by replacing n with 128, passing n in from Python:

tirx::Function Specialize(const tirx::Function& func, const Var& n) {
  ffi::Any result =
      ffi::StructuralMap<ffi::WalkOrder::kPreOrder>(func, [&](const Var& var) -> ffi::Any {
        if (var.same_as(n)) {
          return IntImm(var->ty.as_or_throw<PrimType>(), 128);
        }
        return ffi::Unchanged();
      });
  return result.cast<tirx::Function>();
}

The output is:

from __future__ import annotations

# from tvm_tirx.script import tirx as T

@T.function
def add_one(A: T.Tensor((128,), T.float32), B: T.Tensor((128,), T.float32)):
    for i in range(128):
        B[i] = A[i] + T.float32(1.0)

For every other variable, the callback returns ffi::Unchanged(), which keeps the node as it is. The constant takes its type from the variable, var->ty. As in Python, the mapper keeps definitions and uses consistent, so the new A and B and every use of them carry the specialized shape.

Equality and Hashing#

ffi::StructuralEqual::Equal and ffi::StructuralHash::Hash compare and hash by structure. Let’s compare two add_one functions built separately in Python by make_add(1), the helper from the structural utilities chapter:

ffi::Array<bool> Compare(const tirx::Function& first, const tirx::Function& second) {
  return {
      first.same_as(second),
      ffi::StructuralEqual::Equal(first, second),
      ffi::StructuralHash::Hash(first) == ffi::StructuralHash::Hash(second),
  };
}

The output is:

[False, True, True]

The functions are different objects, yet structurally equal with equal hashes. Equal and Hash also take an optional map_free_vars argument, which defaults to false as in Python.

Visit and Mutate#

When a callback must decide which children to visit, we use ffi::StructuralVisit and ffi::StructuralMutate, as in Python. Their callbacks also receive the visitor or mutator, such as ffi::StructuralVisitorObj*, and descend into a node’s children with DefaultVisitExpected or DefaultMutateExpected.

Visitor and Mutator Classes#

Walk and map cover most tasks. A pass that handles many kinds of node, however, reads better as a class with one method per kind:

Tool

Covers

Use it for

Structural utilities

Any TVM-FFI object

A few node kinds, written as callbacks

tirx::StmtExprVisitor, tirx::StmtExprMutator

TIRx statements and expressions (tvm/tirx/stmt_functor.h)

Passes that customize many node kinds

ExprVisitor, ExprMutator

Expressions alone (tvm/ir/expr_functor.h)

Expression analyses and rewrites

ExprFunctor, tirx::StmtFunctor

Dispatch on the node kind with a signature we choose, such as int(const Expr&), without traversing children

Computations where each hook decides which children to recurse into

Each class declares a virtual hook for every node kind, named Visit_ for a visitor and Mutate_ for a mutator, and a subclass overrides only the kinds it cares about.

These classes are built on the structural utilities. A node kind without a hook, such as a function, falls back to its structural traversal, which hands each child back to our hooks.

Note

ExprVisitor ultimately derives from ffi::StructuralVisitorObj, and ExprMutator from the mutator base behind StructuralMap. Any hook can read the definition region kind with def_region_kind().

Let’s record the loops around each write, as the structural visit example in Python did:

class LoopNestVisitor : public tirx::StmtExprVisitor {
 public:
  using tirx::StmtExprVisitor::Visit_;

  ffi::Optional<ffi::VisitInterrupt> Visit_(const ForObj* loop) override {
    loops_.push_back(loop->var.as<VarObj>()->name);
    ffi::Optional<ffi::VisitInterrupt> result = tirx::StmtExprVisitor::Visit_(loop);
    loops_.pop_back();
    return result;
  }

  ffi::Optional<ffi::VisitInterrupt> Visit_(const TensorStoreObj* store) override {
    std::string entry = std::string(store->dest.as<VarObj>()->name) + " in";
    for (const std::string& loop : loops_) entry += " " + loop;
    writes.push_back(entry);
    return tirx::StmtExprVisitor::Visit_(store);
  }

  ffi::Array<ffi::String> writes;

 private:
  std::vector<std::string> loops_;
};

ffi::Array<ffi::String> LoopsAroundWrites(const tirx::Function& func) {
  auto visitor = ffi::make_object<LoopNestVisitor>();
  visitor->Visit(func);
  return visitor->writes;
}

The output is:

['B in i']

Our For hook pushes the loop variable, calls the base class hook to visit the loop’s bounds and body, then pops the variable. Calling the base hook plays the role of default_visit in Python, and returning its result passes an interrupt from a child up to the caller. Visitors are objects, so we allocate them with ffi::make_object.

Note

The using tirx::StmtExprVisitor::Visit_; line keeps the hooks we did not override visible, as usual for overloaded virtual functions in C++.

A mutator works the same way, with hooks that return the replacement node. Let’s reverse the loop by replacing each use of i with n - 1 - i, built with arithmetic operators as before:

class ReverseLoopMutator : public tirx::StmtExprMutator {
 public:
  using tirx::StmtExprMutator::Mutate_;

  UnchangedOr<Stmt> Mutate_(const ForObj* loop, InplaceMode mode) override {
    reversed_.emplace(loop->var.as<VarObj>(), loop->end - 1 - loop->var);
    return tirx::StmtExprMutator::Mutate_(loop, mode);
  }

  UnchangedOr<Expr> Mutate_(const VarObj* var, InplaceMode mode) override {
    auto it = reversed_.find(var);
    if (it != reversed_.end()) return it->second;
    return tirx::StmtExprMutator::Mutate_(var, mode);
  }

 private:
  std::unordered_map<const VarObj*, PrimExpr> reversed_;
};

tirx::Function ReverseLoop(const tirx::Function& func) {
  auto mutator = ffi::make_object<ReverseLoopMutator>();
  return mutator->Mutate(func).ValueOrUnchanged(func).as_or_throw<tirx::Function>();
}

The output is:

from __future__ import annotations

# from tvm_tirx.script import tirx as T

@T.function
def add_one[n](A: T.Tensor((n,), T.float32), B: T.Tensor((n,), T.float32)):
    for i in range(n):
        B[n - 1 - i] = A[n - 1 - i] + T.float32(1.0)

A mutator hook returns an UnchangedOr<T>: either a replacement node or ffi::Unchanged(), which keeps the original and lets the parents above it stay unchanged too. Our For hook records the replacement before calling the base class hook, so it is ready before any use of i is reached.

Note

StmtExprMutator’s For hook rewrites the loop’s bounds and body but not the loop variable itself, so our Var hook sees only the uses of i, and the loop keeps its variable. The InplaceMode argument tells a hook whether it may update a node that no one else references in place; our hooks forward it to the base class unchanged.

Constraint Contexts#

TIRx adds variants of the structural utilities and the visitor and mutator classes that also pass the facts valid at each node, such as loop ranges and branch conditions:

The functions are in tvm/tirx/structural_visit_with_constraint_context.h and tvm/tirx/structural_mutate_with_constraint_context.h, and the classes in tvm/tirx/stmt_functor_with_constraint_context.h.

These tools follow the same rules as in Python: IR is immutable, rewrites return new programs that share unchanged parts, and every utility respects definitions and uses. Because C++ and Python share the same objects, we can prototype a pass in Python and move parts of it to C++ as needed.
